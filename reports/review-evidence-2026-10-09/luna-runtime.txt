Actionable findings

1. [P2] Accepted shutdown stops authority-silence checks but samples controller loss only twice. Known TODO `shutdown-health-checks`; revalidated at HEAD. In `src/cephvr/supervisor/shutdown.py:482-509`, controller loss is checked before cleanup and after cleanup, while cleanup blocker waits and worker cleanup may run until the original deadline. `src/cephvr/supervisor/health.py:338-366` deliberately suppresses controller/backend heartbeat-loss faults after accepted shutdown. Trigger: a controller is lost after the first checkpoint while a cleanup wait/worker cleanup is in progress. Consequence: active-session interruption is delayed until the second checkpoint, potentially until the cleanup deadline; E06/E08 require controller-loss full shutdown and interruption. Smallest repair: make the existing shutdown coordinator monitor controller identity/heartbeat during bounded waits and interrupt immediately while retaining the same original deadlines (avoid a new lifecycle owner/process). Portable `test_health.py` passes but does not cover loss at this inter-checkpoint point. Governing IDs E06/E08.

2. [P2] Pending error/backend-exit deadlines can start a second safety path after accepted shutdown. Known TODO `shutdown-health-checks`; revalidated. `src/cephvr/supervisor/health.py:330-336` calls `begin_safety` when a pending error expires, and `:399-407` does so for a pending backend exit. The monitor continues calling both at `:414-425`; only `_check_authority_silence` suppresses faults once shutdown is accepted. Trigger: an incident/recovery or backend-exit deadline expires during graceful shutdown. Consequence: `begin_safety` emits a new interruption and calls `retain_shutdown_deadlines` (`shutdown.py:186-209`), potentially changing shutdown intent/operation handling while already executing orderly shutdown. Smallest repair: explicitly reconcile accepted shutdown with pending safety deadlines—either cancel/settle them under the existing shutdown intent, or preserve safety interruption if it is still required—without extending original budgets. Add a focused test for an expiry during the accepted shutdown. E06/E08.

3. [P2] Python worker launch entries have no normal release path. Known TODO `worker-launch-retirement`; revalidated, not a new regression in this delta. `src/cephvr/supervisor/registry.py:430-452` has exact release and releases the native job/retained process handle only after all obligations are met. The call sites found are native helper reconciliation (`supervisor/acquisition_worker.py:342`), firmware release, and GUI release (`registry.py:454+`); `visual_stimulus_worker.py` confirms cleanup completion but never releases its worker launch. Cleanup/shutdown worker operations do not release worker launch records. Trigger: workers finish their lifetime/cleanup and their retained launch entries remain in the registry through the app run. Consequence: launch identities and handles persist and eventually consume bounded launch capacity; a later legitimate launch can be rejected at capacity, or stale status retained. Smallest repair: release each worker only after exact process/job absence plus retained worker cleanup/closure proof; ensure release notification retires its cached channel. Do not equate Cleanup admission with closure. Tests establish release behavior/capacity mechanics, but not owner-side retirement.

4. [P2, low] PlanLaunch idempotency ends when capacity pruning removes RELEASED records. Known TODO `pruned-launch-replay`; revalidated by source and existing test. `src/cephvr/supervisor/registry.py:94-106` prunes the oldest released entries only when at capacity; then `plan()` at `:160-178` sees a reused command ID as new and creates another containment job. Trigger: caller retries an old PlanLaunch after its release entry was pruned at capacity. Consequence: same command ID can create a second job instead of returning the original terminal receipt, violating durable-enough idempotent replay semantics. Smallest repair: retain a bounded compact tombstone/digest or explicitly reject expired identities, rather than silently treating same ID as new. Existing `tests/supervisor/test_registry.py` documents replay only before pruning and pruning capacity, and the focused tests pass. E08.

5. [P2, rare crash window] A mid-session late-Finished recovery event is parsed as terminal recovery on next startup. Known TODO `late-finished-recovery`; revalidated. `src/cephvr/controller/lifecycle_completion.py:241-263` appends a `recovery` event as soon as exact late Finished evidence is accepted, even if the session is still active. `src/cephvr/controller/recovery_inspection.py:181-184, 221-226` treats any completed `recovery` event as final and rejects subsequent records. Trigger: a late Finished occurs, more normal session events are written, then the app crashes before the reservation marker is completed. Consequence: intact administrative log is classified unconfirmed and startup recovery is blocked. Smallest repair: mark/reconcile this event as nonterminal or defer terminal `recovery` record until session-end recovery; maintain evidence that preserves the late result. Existing lifecycle report tests pass but don't exercise crash/startup inspection after a mid-session late Finished. E04/E06.

6. [P3] Duplicate command IDs bypass the shared operation helper for Setup and Start. Known controller audit observation; revalidated, but impact is limited because lifecycle admission gates avoid concurrent replay. `src/cephvr/controller/lifecycle/setup_admission.py:424-429` and `src/cephvr/controller/lifecycle/start.py:103-108` assign directly into `control.operations`. The intended duplicate guard is `src/cephvr/controller/control/operations.py:39-55`; `authorized()` does not check ID collision (`:125+`). Trigger: reuse an already retained command ID for Setup/Start after the original operation is no longer the current phase. Consequence: overwrites historical command outcome, so later status query may return the new operation under an old ID. Smallest repair: use the existing `operation()` allocator or shared duplicate-ID check before inserting. No claim of duplicate execution established. E02/E08 command identity/idempotency.

7. [P3] Shutdown before session activation does not cancel Setup prompt futures. Known controller audit observation; revalidated. `src/cephvr/controller/lifecycle/commands.py:249-260` sets cancellation and launches cleanup but does not cancel pending `incident_state.prompts` futures; the analogous explicit Cancel Setup path does (`lifecycle/cleanup.py:368-395`). Trigger: Shutdown Application during Setup while a Continue/Cancel prompt is unresolved. Consequence: Setup coroutine can remain parked on a prompt until another response/deadline even as cleanup/shutdown proceeds, delaying truthful completion/settlement. Smallest repair: route through the same per-attempt prompt cancellation helper used by Cancel Setup. Portable chosen tests did not cover this prompt race. E05/E06/E08.

8. [P3] Reservation failure warning is mutated outside lifecycle lock during cancel-attempt completion. Known controller audit observation; revalidated. `src/cephvr/controller/lifecycle/cleanup.py:255-257` appends warning before acquiring `lifecycle.lock` at `:260`; snapshots and other warning writes are coordinated with that lock. Trigger: reservation cleanup failure while another event-loop operation publishes/mutates warnings. Consequence: possible snapshot observing a partially ordered warning update or lost update; impact is operator diagnostics, not reservation proof. Smallest repair: stage the failure text locally and append it under the existing lock immediately before publish. Existing behavior has no failure evidence from these tests; make a focused lock-order test if fixed.
